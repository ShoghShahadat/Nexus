بخش ۲۵: نوشتن سیستم‌های سفارشی - بهترین شیوه‌ها

یک راهنمای عملی برای طراحی سیستم‌های کارآمد، قابل نگهداری و قابل استفاده مجدد.

هنر طراحی سیستم

نوشتن یک سیستم کار سختی نیست، اما نوشتن یک سیستم خوب نیازمند تفکر و رعایت چند اصل کلیدی است. سیستم‌ها قلب تپنده منطق اپلیکیشن شما هستند و طراحی صحیح آن‌ها تفاوت بین یک پروژه تمیز و قابل نگهداری با یک پروژه شلخته و پیچیده را رقم می‌زند.

در این بخش، ما مجموعه‌ای از بهترین شیوه‌ها و نکات را برای طراحی سیستم‌های سفارشی شما مرور می‌کنیم.

۱. اصل تک‌مسئولیتی (Single Responsibility Principle)

هر سیستم باید فقط و فقط یک مسئولیت مشخص داشته باشد. از ساختن "سیستم‌های همه‌کاره" که چندین کار نامرتبط را انجام می‌دهند، به شدت پرهیز کنید.

  • بد: یک `GameplaySystem` که هم حرکت بازیکن، هم منطق برخورد و هم سیستم سلامتی را مدیریت می‌کند.
  • خوب: سه سیستم مجزا: `MovementSystem`, `CollisionSystem`, `HealthSystem`.

این اصل باعث می‌شود سیستم‌های شما کوچک، متمرکز، قابل فهم و قابل استفاده مجدد باشند.

۲. سیستم‌های خود را "کور" طراحی کنید

یک سیستم خوب نباید بداند که روی چه "نوع" موجودیتی کار می‌کند. او فقط به "ترکیب کامپوننت‌ها" اهمیت می‌دهد. 


// بد: این سیستم فقط روی "بازیکن" کار می‌کند
@override
bool matches(Entity entity) {
  return entity.get()?.hasTag('player') ?? false;
}

// خوب: این سیستم روی "هر چیزی" که سلامتی دارد کار می‌کند
@override
bool matches(Entity entity) {
  return entity.has();
}

با طراحی به روش دوم، `HealthSystem` شما می‌تواند منطق سلامتی را هم برای بازیکن، هم برای دشمنان و هم برای جعبه‌های شکستنی اعمال کند، بدون اینکه هیچ تغییری در کد آن لازم باشد.

۳. `update` در مقابل `listen`: کدام را انتخاب کنیم؟

یک تصمیم مهم در طراحی سیستم، انتخاب بین منطق مبتنی بر فریم (`update`) و منطق مبتنی بر رویداد (`listen`) است.

  • از `update` برای فرآیندهای مداوم استفاده کنید که باید در هر فریم اجرا شوند. (مثال: فیزیک، انیمیشن، شمارش معکوس).
  • از `listen` برای فرآیندهای واکنشی استفاده کنید که فقط در پاسخ به یک اتفاق خاص باید اجرا شوند. (مثال: کلیک دکمه، دریافت پیام از شبکه، اتمام یک تایمر).

استفاده صحیح از `listen` به جای `update` در موارد ممکن، به طور قابل توجهی عملکرد برنامه را بهبود می‌بخشد، زیرا از اجرای کدهای غیرضروری در هر فریم جلوگیری می‌کند.

۴. سیستم‌ها نباید وضعیت داخلی داشته باشند (تا حد امکان)

سعی کنید سیستم‌های شما بدون حالت (stateless) باشند. تمام وضعیت برنامه باید در کامپوننت‌ها ذخیره شود. سیستم فقط باید این داده‌ها را بخواند، پردازش کند و نتیجه را دوباره در کامپوننت‌ها بنویسد.

  • بد: `class PlayerSystem { bool isJumping = false; ... }`
  • خوب: `playerEntity.add(IsJumpingComponent())` و `PlayerSystem` فقط وجود این کامپوننت را بررسی می‌کند.

این اصل، پیش‌بینی رفتار سیستم و دیباگ کردن آن را بسیار ساده‌تر می‌کند، زیرا وضعیت کل برنامه همیشه در یک مکان مشخص (کامپوننت‌های موجودیت‌ها) قرار دارد.

قانون طلایی

همیشه از خود بپرسید: "آیا می‌توانم این منطق را به یک سیستم عمومی‌تر و قابل استفاده مجدد تبدیل کنم؟" به جای نوشتن یک `PlayerMovementSystem`، یک `MovementSystem` بنویسید که روی هر موجودیت دارای `VelocityComponent` و `PositionComponent` کار کند. این طرز فکر، هسته اصلی قدرت معماری ECS است.
