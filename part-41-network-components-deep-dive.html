مستندات پروژه-محور Nexus

بخش ۴۱: غواصی عمیق در کامپوننت‌های شبکه

الگوی Command برای مدیریت درخواست‌های HTTP و ارتباطات WebSocket.

فلسفه وجودی: شبکه به عنوان یک فرمان

در معماری‌های سنتی، فراخوانی‌های شبکه اغلب مستقیماً از درون کنترلرها، ViewModelها یا BLoCها انجام می‌شود. این کار منطق کسب‌وکار را با جزئیات پیاده‌سازی شبکه (مانند مدیریت خطا، پارس کردن JSON) در هم می‌آمیزد.

Nexus یک رویکرد متفاوت را ترویج می‌کند: یک درخواست شبکه، یک "فرمان" (Command) است که شما صادر می‌کنید. شما به عنوان یک سیستم، فقط می‌گویید "من به این داده از این URL نیاز دارم" و جزئیات اجرای این فرمان را به سیستم‌های تخصصی شبکه واگذار می‌کنید.

`ApiRequestComponent` و `WebSocketRequestComponent` پیاده‌سازی‌های الگوی Command در Nexus هستند. این‌ها کامپوننت‌های منطقی (logic-only) و یکبار مصرف هستند.

کالبدشکافی `ApiRequestComponent`

این کامپوننت یک درخواست HTTP کامل را توصیف می‌کند. 


// از پکیج nexus

class ApiRequestComponent extends Component {
  final String url;
  final HttpMethod method;
  final Map? body;
  
  // مهم‌ترین بخش: تابعی که پاسخ JSON را به کامپوننت‌های داده ترجمه می‌کند
  final List Function(Map json) onParse;
  
  // رویدادهای اختیاری برای اطلاع‌رسانی به سایر سیستم‌ها
  final dynamic onSuccessEvent;
  final dynamic onErrorEvent;
}

نکته کلیدی در اینجا تابع `onParse` است. این تابع، مرز بین دنیای خارج (ساختار JSON سرور) و دنیای داخل (ساختار کامپوننت‌های شما) را تعریف می‌کند. `ApiSystem` هیچ دانشی در مورد نحوه پارس کردن داده‌های شما ندارد؛ این مسئولیت کاملاً به عهده شماست که در زمان صدور فرمان، آن را مشخص کنید.

کالبدشکافی `WebSocketRequestComponent`

این کامپوننت مشابه `ApiRequestComponent` است، اما برای یک اتصال پایدار طراحی شده است. 


// از پکیج nexus

class WebSocketRequestComponent extends Component {
  final String url;
  
  // این تابع برای "هر پیام" دریافتی از سوکت فراخوانی می‌شود
  final List Function(dynamic data) onParseMessage;
  
  final dynamic onConnectedEvent;
  final dynamic onDisconnectedEvent;
}

`WebSocketSystem` پس از برقراری اتصال، این کامپوننت را حذف می‌کند، اما تابع `onParseMessage` را در حافظه نگه می‌دارد تا برای هر پیام ورودی از آن استفاده کند.

مقایسه با Repository Pattern

این الگو شباهت‌هایی به الگوی Repository دارد. `ApiSystem` و `WebSocketSystem` مانند یک Repository عمل می‌کنند که جزئیات دسترسی به داده را از بقیه برنامه پنهان می‌کنند.

اما یک تفاوت مهم وجود دارد: در Nexus، نتیجه یک درخواست شبکه، مستقیماً به صورت تغییر وضعیت در دنیای ECS (افزودن کامپوننت‌های جدید) اعمال می‌شود. در الگوی Repository سنتی، شما معمولاً یک مدل داده (DTO) را برمی‌گردانید و سپس باید به صورت دستی وضعیت برنامه (مثلاً در یک BLoC) را با آن داده جدید به‌روز کنید. رویکرد Nexus این دو مرحله را در یک فرآیند یکپارچه و داده-محور ترکیب می‌کند.

نتیجه: سیستم‌های خالص و تست‌پذیر

با استفاده از این الگو، سیستم‌های منطقی شما (مانند `ProfileSystem` در پروژه نمونه) نیازی به دانستن چیزی در مورد `Dio`, `http` یا `WebSocket` ندارند. آن‌ها فقط کامپوننت‌های فرمان را می‌سازند و به موجودیت‌ها اضافه می‌کنند.

این جداسازی، تست کردن سیستم‌های شما را فوق‌العاده آسان می‌کند. شما می‌توانید به راحتی `ApiSystem` را در تست‌ها mock کنید و بررسی کنید که آیا سیستم شما در پاسخ به یک رویداد، `ApiRequestComponent` صحیح را صادر می‌کند یا خیر، بدون اینکه نیاز به یک سرور واقعی داشته باشید.
