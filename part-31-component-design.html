مستندات پروژه-محور Nexus

بخش ۳۱: هنر طراحی کامپوننت

چگونه کامپوننت‌هایی طراحی کنیم که داده‌ها را به صورت بهینه، قابل ترکیب و قابل نگهداری مدل‌سازی کنند.

کامپوننت: اتم‌های سازنده دنیا

کامپوننت‌ها، اتم‌های دنیای Nexus شما هستند. آن‌ها کوچکترین واحدهای داده‌ای هستند که هویت و وضعیت موجودیت‌ها را تعریف می‌کنند. طراحی صحیح کامپوننت‌ها، بیشترین تأثیر را بر کیفیت، انعطاف‌پذیری و عملکرد معماری شما دارد. یک کامپوننت خوب، کوچک، متمرکز و تغییرناپذیر (immutable) است.

انواع کامپوننت‌ها و کاربردهایشان

در عمل، ما می‌توانیم کامپوننت‌ها را به چند دسته اصلی تقسیم کنیم:

  1. کامپوننت داده (Data Component): رایج‌ترین نوع. این کامپوننت‌ها داده‌های خام را نگهداری می‌کنند. مثال: `PositionComponent`, `HealthComponent`.
  2. کامپوننت نشانگر (Marker Component): این کامپوننت‌ها هیچ داده‌ای ندارند و صرفاً وجودشان بر روی یک موجودیت، یک وضعیت `bool` را نشان می‌دهد. مثال: `IsDeadComponent`, `EditingCategoryComponent`.
  3. کامپوننت وضعیت (State Component): این کامپوننت‌ها یک وضعیت پیچیده‌تر را با استفاده از `enum` مدل‌سازی می‌کنند و اغلب به عنوان ماشین وضعیت عمل می‌کنند. مثال: `ApiStatusComponent`.

اصل کلیدی: ترکیب بر ارث‌بری (Composition over Inheritance)

بیایید یک سناریو را با دو معماری مقایسه کنیم. می‌خواهیم یک دشمن در بازی بسازیم که هم پرواز می‌کند و هم آتش شلیک می‌کند.

رویکرد سنتی (ارث‌بری):


abstract class Enemy { void update(); }
abstract class FlyingEnemy extends Enemy { void fly(); }
abstract class ShootingEnemy extends Enemy { void shoot(); }

// مشکل: برای دشمنی که هم پرواز می‌کند و هم شلیک می‌کند، چه کنیم؟
class FlyingShootingEnemy extends FlyingEnemy { // یا ShootingEnemy؟
  // باید منطق هر دو را کپی یا ترکیب کنیم. این به "diamond problem" معروف است.
}

رویکرد Nexus (ترکیب):


// کامپوننت‌های نشانگر برای قابلیت‌ها
class CanFlyComponent extends Component {}
class CanShootComponent extends Component { final double fireRate; ... }

// سیستم‌های مجزا برای هر قابلیت
class FlightSystem extends System { /* منطق پرواز */ }
class ShootingSystem extends System { /* منطق شلیک */ }

// ساخت موجودیت با ترکیب قابلیت‌ها
final myEnemy = Entity()
  ..add(EnemyTagComponent())
  ..add(CanFlyComponent())
  ..add(CanShootComponent(fireRate: 2.0));

در رویکرد Nexus، ما به سادگی با افزودن کامپوننت‌ها، قابلیت‌ها را به موجودیت "می‌چسبانیم". این روش بی‌نهایت انعطاف‌پذیرتر است. فردا می‌توانیم یک `CanSwimComponent` و `SwimmingSystem` اضافه کنیم و دشمن ما می‌تواند شنا هم بکند، بدون اینکه ساختار کلاس‌های موجود را تغییر دهیم.

طراحی برای تغییرناپذیری (Immutability)

یک اصل مهم در طراحی کامپوننت‌ها، تغییرناپذیری است. این یعنی به جای تغییر مقادیر داخلی یک کامپوننت، شما همیشه یک نمونه جدید از آن را با مقادیر به‌روز شده می‌سازید. 


// بد: تغییر مستقیم داده (Mutable)
final pos = entity.get()!;
pos.x += 10; // این تغییر توسط فریم‌ورک به راحتی قابل ردیابی نیست.

// خوب: ساخت نمونه جدید (Immutable)
final pos = entity.get()!;
final newPos = PositionComponent(x: pos.x + 10, y: pos.y);
entity.add(newPos); // فریم‌ورک این جایگزینی را به عنوان یک تغییر تشخیص می‌دهد.

استفاده از `final` برای فیلدهای کامپوننت، این اصل را تقویت می‌کند. این رویکرد، جریان داده را قابل پیش‌بینی کرده و به `EquatableMixin` اجازه می‌دهد تا به درستی تشخیص دهد که آیا داده واقعاً تغییر کرده است یا خیر، که برای بهینه‌سازی UI حیاتی است.

مقایسه با BLoC/Cubit

در BLoC، ما معمولاً یک کلاس `State` بزرگ داریم که تمام وضعیت یک صفحه را در خود نگه می‌دارد. با هر تغییر کوچک، باید یک کپی از کل این کلاس `State` با متد `copyWith` بسازیم. در Nexus، ما وضعیت را به کامپوننت‌های کوچک و مستقل می‌شکنیم. این یعنی وقتی فقط موقعیت تغییر می‌کند، ما فقط یک `PositionComponent` جدید می‌سازیم، نه یک کپی از کل وضعیت موجودیت. این رویکرد، مدیریت وضعیت را دانه‌ریزتر (more granular) و کارآمدتر می‌کند.
