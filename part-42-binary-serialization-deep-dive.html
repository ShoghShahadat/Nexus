بخش ۴۲: غواصی عمیق در سریال‌سازی باینری

چه زمانی و چگونه از فرمت باینری برای حداکثر کارایی در شبکه و ذخیره‌سازی استفاده کنیم.

JSON در مقابل باینری: یک انتخاب استراتژیک

در بخش ۲۱، ما با دو نوع سریال‌سازی در Nexus آشنا شدیم. سریال‌سازی JSON به دلیل خوانایی بالا، برای ارتباط با UI و ذخیره‌سازی‌های ساده ایده‌آل است. اما برای سناریوهای پرفورمنس-محور مانند بازی‌های چندنفره آنلاین، حجم داده‌های JSON می‌تواند به یک گلوگاه تبدیل شود.

سریال‌سازی باینری، داده‌ها را به یک فرمت بسیار فشرده و کارآمد تبدیل می‌کند که هم حجم کمتری دارد و هم پردازش (encode/decode) آن سریع‌تر است.

پیاده‌سازی `BinaryComponent`

برای اینکه یک کامپوننت قابل سریال‌سازی باینری باشد، باید mixin `BinaryComponent` را پیاده‌سازی کند. این mixin شما را ملزم به پیاده‌سازی سه عضو می‌کند: 


// از پکیج nexus

mixin BinaryComponent on Component {
  // ۱. یک شناسه عددی منحصر به فرد در کل پروژه
  int get typeId;

  // ۲. منطق نوشتن داده‌ها در یک بافر باینری
  void toBinary(BinaryWriter writer);

  // ۳. منطق خواندن داده‌ها از یک بافر باینری
  void fromBinary(BinaryReader reader);
}

مثال: `HealthComponent`


class HealthComponent extends Component with SerializableComponent, BinaryComponent {
  late double currentHealth;
  late double maxHealth;

  // ... کانستراکتور و متدهای JSON ...

  @override
  int get typeId => 3; // شناسه منحصر به فرد برای HealthComponent

  @override
  void toBinary(BinaryWriter writer) {
    // فقط داده‌های دینامیک را ارسال می‌کنیم تا در پهنای باند صرفه‌جویی شود
    writer.writeDouble(currentHealth);
  }

  @override
  void fromBinary(BinaryReader reader) {
    currentHealth = reader.readDouble();
    // maxHealth از داده‌های اولیه موجودیت خوانده می‌شود و از شبکه نمی‌آید
  }
}

نکته مهم در این مثال، بهینه‌سازی است. ما `maxHealth` را که معمولاً یک مقدار ثابت است، از طریق شبکه ارسال نمی‌کنیم. کلاینت از قبل این مقدار را می‌داند و فقط `currentHealth` را که به طور مداوم تغییر می‌کند، دریافت می‌کند.

`BinaryWorldSerializer`: مترجم دنیای باینری

این کلاس مسئولیت تبدیل لیستی از موجودیت‌ها به یک آرایه بایت (`Uint8List`) و برعکس را بر عهده دارد.

فرآیند سریال‌سازی:

  1. تعداد موجودیت‌ها را می‌نویسد.
  2. برای هر موجودیت:
    • شناسه موجودیت (`entity.id`) را می‌نویسد.
    • تعداد کامپوننت‌های باینری آن را می‌نویسد.
    • برای هر کامپوننت:
      • شناسه نوع کامپوننت (`typeId`) را می‌نویسد.
      • متد `toBinary` آن کامپوننت را فراخوانی می‌کند.

فرآیند دی‌سریال‌سازی دقیقاً برعکس این مراحل است و از `BinaryComponentFactory` برای ساخت نمونه‌های خالی کامپوننت‌ها بر اساس `typeId` استفاده می‌کند.

چه زمانی از باینری استفاده کنیم؟

به عنوان یک قانون کلی، هر زمان که داده‌ها باید از طریق شبکه بین دو برنامه (مثلاً کلاینت و سرور بازی) رد و بدل شوند، سریال‌سازی باینری انتخاب ارجح است. برای تمام موارد دیگر (ارتباط با UI، ذخیره‌سازی محلی)، سریال‌سازی JSON معمولاً ساده‌تر و کافی است.

یک کامپوننت می‌تواند هر دو mixin را داشته باشد تا در هر دو سناریو قابل استفاده باشد، همانطور که در مثال `HealthComponent` دیدیم.
