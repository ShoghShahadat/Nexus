مستندات پروژه-محور Nexus

بخش ۳: موجودیت‌ها و کامپوننت‌ها

آشنایی با آجرهای سازنده معماری ECS: "چیزها" (Entities) و "داده‌هایشان" (Components).

تفکیک هویت از داده

در دو بخش قبل، با تصویر کلی معماری ECS و نحوه برپایی `NexusWorld` آشنا شدیم. اکنون زمان آن رسیده که به دو جزء از سه جزء اصلی این معماری یعنی Entity و Component بپردازیم. درک صحیح این دو مفهوم، کلید تسلط بر فریم‌ورک Nexus است.

Entity: یک شناسه خالی

یک Entity در ساده‌ترین حالت ممکن، فقط یک شناسه (ID) منحصربه‌فرد است. همین! یک موجودیت به خودی خود هیچ داده، رفتار یا هویتی ندارد. این یک بوم خالی است که ما می‌توانیم با افزودن کامپوننت‌ها، آن را به هر چیزی که می‌خواهیم تبدیل کنیم.

موجودیت‌ها توسط کلاس `EntityProvider` در هر ماژول ساخته و به `NexusWorld` اضافه می‌شوند. بیایید به یک مثال از `AppBarModule` نگاه کنیم: 


// File: lib/src/app_bar/app_bar_module.dart

class AppBarEntityProvider extends EntityProvider {
  @override
  void createEntities(NexusWorld world) {
    // 1. یک موجودیت جدید و خالی ساخته می‌شود
    final appBarEntity = Entity()
      // 2. به آن کامپوننت اضافه می‌کنیم تا هویت بگیرد
      ..add(TagsComponent({'app_bar'}))
      ..add(AppBarComponent(title: 'داشبورد')) // داده اولیه
      ..add(LifecyclePolicyComponent(isPersistent: true));
    
    // 3. موجودیت را به دنیا اضافه می‌کنیم
    world.addEntity(appBarEntity);
  }
}

Component: داده خالص و بدون منطق

اگر Entity یک بوم خالی است، Component رنگ و قلم‌مویی است که ما برای نقاشی روی آن بوم استفاده می‌کنیم. یک کامپوننت، یک کلاس داده خالص است. این یعنی فقط داده دارد و هیچ منطقی برای پردازش آن داده در خود ندارد.

غواصی عمیق: `AppBarComponent`

بیایید به یک مثال واقعی از پروژه نگاه کنیم. فایل `lib/src/app_bar/app_bar_module.dart` را باز کنید. 


// File: lib/src/app_bar/app_bar_module.dart

class AppBarComponent extends Component with SerializableComponent {
  final String title;

  AppBarComponent({required this.title});

  // متد برای تبدیل به JSON
  @override
  Map toJson() => {'title': title};

  // کانستراکتور برای ساخت از JSON
  factory AppBarComponent.fromJson(Map json) {
    return AppBarComponent(title: json['title']);
  }

  // برای مقایسه و بهینه‌سازی (مهم!)
  @override
  List get props => [title];
}

همانطور که می‌بینید، این کلاس فقط یک پراپرتی `title` دارد. وظیفه آن فقط و فقط نگهداری داده است.

قدرت `SerializableComponent` و `EquatableMixin`

دو `mixin` مهم در تعریف کامپوننت بالا وجود دارد:

  • `SerializableComponent`: این mixin کامپوننت را موظف می‌کند تا متدهای `toJson` و `fromJson` را پیاده‌سازی کند. این قابلیت برای ارتباط بین ایزولیت‌ها و ذخیره‌سازی وضعیت برنامه حیاتی است.
  • `EquatableMixin` (که در کلاس `Component` پایه وجود دارد): این mixin با استفاده از `props`، مقایسه دو نمونه از کامپوننت را بر اساس مقادیر داخلی‌شان ممکن می‌سازد، نه بر اساس آدرس حافظه. این برای بهینه‌سازی عملکرد UI بسیار مهم است، زیرا فریم‌ورک می‌تواند تشخیص دهد که آیا داده واقعاً تغییر کرده است یا خیر.

نگاهی دیگر: `NavigationStateComponent`

در فایل `lib/src/drawer/drawer_module.dart`، کامپوننت `NavigationStateComponent` را پیدا کنید. این کامپوننت کمی پیچیده‌تر است و لیستی از آیتم‌های منو (`items`) و شناسه آیتم انتخاب شده (`selectedItemId`) را نگهداری می‌کند. این یک مثال عالی دیگر از این است که چگونه داده‌های مربوط به یک ویژگی، در یک کامپوننت کپسوله می‌شوند.

جمع‌بندی

تا اینجا یاد گرفتیم:

  • Entity یک شناسه است که با `new Entity()` ساخته می‌شود.
  • Component داده‌های مربوط به یک شناسه است.
  • یک Entity می‌تواند چندین Component داشته باشد و هویت آن از ترکیب کامپوننت‌هایش شکل می‌گیرد.

اما سوال اصلی باقی می‌ماند: چه کسی این داده‌ها را می‌خواند، پردازش می‌کند و تغییر می‌دهد؟ پاسخ این سوال در بخش بعدی نهفته است: سیستم‌ها (Systems)، مغز متفکر معماری ما.
