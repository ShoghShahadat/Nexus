مستندات پروژه-محور Nexus

بخش ۳۵: موتور قوانین واکنشی (Rule Engine)

چگونه با `RuleSystem` از شر `if/else` های تودرتو خلاص شویم و منطق را به صورت اعلامی (Declarative) بنویسیم.

مشکل: منطق پراکنده و پیچیده

در بسیاری از اپلیکیشن‌ها، منطق کسب‌وکار به صورت زنجیره‌ای از `if/else` یا `switch` در متدهای مختلف پخش می‌شود. برای مثال، "اگر کاربر وارد شد و اشتراک ویژه داشت و این اولین ورودش در این ماه بود، به او یک جایزه بده". پیاده‌سازی و نگهداری چنین منطق‌هایی به سرعت پیچیده و مستعد خطا می‌شود.

راه حل Nexus: منطق به عنوان داده

`RuleSystem` و `RuleComponent` به شما اجازه می‌دهند تا این منطق‌ها را به جای کد دستوری (Imperative)، به صورت داده‌های اعلامی (Declarative) تعریف کنید. شما "قوانین" را به عنوان داده به موجودیت‌ها اضافه می‌کنید و `RuleSystem` مسئولیت اجرای آن‌ها را بر عهده می‌گیرد.

هر قانون در `RuleComponent` از سه بخش تشکیل شده است:

  • triggers: لیستی از انواع رویدادها. این قانون فقط زمانی ارزیابی می‌شود که یکی از این رویدادها رخ دهد.
  • condition: یک تابع که `true` یا `false` برمی‌گرداند. این تابع، شرط اصلی اجرای قانون است.
  • actions: یک تابع که در صورت `true` بودن شرط، اجرا می‌شود.

مثال عملی: سیستم دستاوردها (Achievements)

بیایید یک سیستم دستاورد برای یک بازی طراحی کنیم. می‌خواهیم دستاورد "قاتل گابلین‌ها" را داشته باشیم که پس از کشتن ۱۰ گابلین، باز می‌شود.

رویکرد سنتی (بدون RuleSystem):


// یک سیستم بزرگ که همه چیز را مدیریت می‌کند
class AchievementSystem extends System {
  void _onEnemyDefeated(EnemyDefeatedEvent event) {
    if (event.type == 'goblin') {
      final stats = world.rootEntity.get()!;
      stats.goblinKills++;
      if (stats.goblinKills == 10) {
        if (!stats.hasGoblinSlayerAchievement) {
          stats.hasGoblinSlayerAchievement = true;
          world.eventBus.fire(AchievementUnlockedEvent('Goblin Slayer'));
        }
      }
      world.rootEntity.add(stats);
    }
    // ... ده‌ها if/else دیگر برای سایر دستاوردها ...
  }
}

رویکرد Nexus (با RuleSystem):

در این روش، ما یک موجودیت برای خود دستاورد می‌سازیم و منطق آن را به عنوان داده به آن اضافه می‌کنیم. 


// در EntityProvider
final goblinSlayerAchievement = Entity()
  ..add(AchievementDataComponent(name: 'Goblin Slayer', isUnlocked: false))
  ..add(RuleComponent(
    triggers: {EnemyDefeatedEvent}, // فقط به این رویداد واکنش نشان بده
    condition: (entity, event) {
      // شرط: آیا این دستاورد هنوز باز نشده؟
      if (entity.get()!.isUnlocked) return false;
      
      // آیا دشمن کشته شده گابلین است؟
      if ((event as EnemyDefeatedEvent).type != 'goblin') return false;
      
      // آیا تعداد کشته‌ها به ۱۰ رسیده؟
      final stats = world.rootEntity.get()!;
      return stats.goblinKills >= 10;
    },
    actions: (entity, event) {
      // اقدام: دستاورد را باز کن و رویداد را منتشر کن
      entity.add(AchievementDataComponent(name: 'Goblin Slayer', isUnlocked: true));
      world.eventBus.fire(AchievementUnlockedEvent('Goblin Slayer'));
    },
  ));
world.addEntity(goblinSlayerAchievement);

مقایسه و مزایا

در رویکرد دوم، `AchievementSystem` به طور کامل حذف می‌شود! `RuleSystem` که یک سیستم عمومی است، تمام کارها را انجام می‌دهد. منطق هر دستاورد به صورت مستقل و کپسوله شده در کنار داده‌های خود آن دستاورد قرار دارد.

  • افزودن دستاوردهای جدید: فقط کافیست یک موجودیت جدید با `RuleComponent` جدید بسازید. نیازی به تغییر هیچ سیستمی نیست.
  • خوانایی بالا: منطق هر دستاورد به صورت یک واحد کامل (محرک، شرط، اقدام) قابل خواندن است.
  • تست‌پذیری: شما می‌توانید به راحتی `RuleComponent` را به صورت مستقل تست کنید.

`RuleSystem` به شما اجازه می‌دهد تا از برنامه‌نویسی دستوری به سمت یک رویکرد اعلامی و داده-محور حرکت کنید، که این یکی از قدرتمندترین مفاهیم در طراحی نرم‌افزارهای مقیاس‌پذیر است.
