مستندات پروژه-محور Nexus

بخش ۴۸: گسترش فریم‌ورک Nexus

چگونه ابزارهای قابل استفاده مجدد خود را بسازیم و Nexus را برای نیازهای خاص خود سفارشی کنیم.

از مصرف‌کننده به سازنده

تاکنون، ما از کامپوننت‌ها و سیستم‌های هسته‌ای Nexus به عنوان ابزارهای آماده استفاده کرده‌ایم. اما قدرت واقعی یک فریم‌ورک زمانی آشکار می‌شود که شما شروع به ساختن ابزارهای خود بر پایه آن می‌کنید. Nexus به گونه‌ای طراحی شده که به شدت قابل گسترش باشد.

در این بخش، ما یاد می‌گیریم که چگونه با ساختن سیستم‌ها، کامپوننت‌ها و بیلدرهای عمومی، فریم‌ورک را برای حل مشکلات خاص دامنه خود گسترش دهیم.

ساخت یک سیستم هسته‌ای سفارشی: `TweenSystem`

`AnimationComponent` برای انیمیشن‌های ساده خوب است، اما برای انیمیشن‌های پیچیده‌تر که نیاز به درون‌یابی مقادیر دارند (tweening)، می‌توانیم یک راه‌حل عمومی‌تر بسازیم.

  1. `TweenComponent` (کامپوننت): این کامپوننت یک انیمیشن را تعریف می‌کند: مقدار شروع، مقدار پایان، مدت زمان، منحنی، و یک `onUpdate` callback که مقدار درون‌یابی شده فعلی را دریافت می‌کند.
  2. `TweenSystem` (سیستم): این سیستم در حلقه `update`، پیشرفت انیمیشن را محاسبه کرده، مقدار فعلی را با استفاده از منحنی درون‌یابی می‌کند و `onUpdate` callback را با مقدار جدید فراخوانی می‌کند.

// کامپوننت داده برای تعریف یک tween
class TweenComponent extends Component {
  final double begin;
  final double end;
  final Duration duration;
  final Curve curve;
  final void Function(Entity entity, double value) onUpdate;
  // ... وضعیت داخلی مانند elapsedTime
}

// سیستم عمومی برای پردازش تمام TweenComponent ها
class TweenSystem extends System {
  @override
  bool matches(Entity entity) => entity.has();

  @override
  void update(Entity entity, double dt) {
    final tween = entity.get()!;
    // ... محاسبه پیشرفت و مقدار درون‌یابی شده ...
    final currentValue = tween.curve.transform(progress) * (tween.end - tween.begin) + tween.begin;
    tween.onUpdate(entity, currentValue);
    // ...
  }
}

با ساختن این دو، شما اکنون یک سیستم انیمیشن tweening قابل استفاده مجدد دارید که می‌توانید در هر پروژه‌ای از آن استفاده کنید.

ساخت یک `IWidgetBuilder` عمومی: `DataGridBuilder`

تصور کنید در اپلیکیشن خود به چندین جدول یا گرید داده نیاز دارید. به جای نوشتن کد تکراری برای هر کدام، می‌توانید یک `DataGridBuilder` عمومی بسازید.

این بیلدر می‌تواند به یک موجودیت مدیر لیست (که `ListComponent` دارد) گوش دهد. سپس با استفاده از داده‌های `visibleItems`، یک ویجت گرید (مانند `DataTable` یا `PaginatedDataTable`) را رندر کند. این بیلدر می‌تواند پارامترهای پیکربندی را از یک کامپوننت سفارشی مانند `DataGridStyleComponent` بخواند تا ظاهر گرید را سفارشی‌سازی کند.

ادغام با پکیج‌های دیگر: مثال `fl_chart`

فرض کنید می‌خواهیم از پکیج `fl_chart` برای نمایش نمودار استفاده کنیم. بهترین روش، ساخت یک "پل" (Bridge) است:

  1. `ChartDataComponent`: یک کامپوننت `Serializable` که داده‌های نمودار را به فرمتی ساده و مستقل از `fl_chart` نگه می‌دارد (مثلاً `List`).
  2. `ChartPresenterSystem`: این سیستم داده‌های خام شما (مثلاً از یک `ApiStatusComponent`) را گرفته و آن‌ها را به فرمت `ChartDataComponent` تبدیل می‌کند.
  3. `ChartBuilder` (یک `IWidgetBuilder`): این بیلدر به `ChartDataComponent` گوش می‌دهد، داده‌های آن را به فرمت مورد نیاز ویجت‌های `fl_chart` (مانند `LineChartBarData`) تبدیل کرده و ویجت نمودار را رندر می‌کند.

با این روش، دنیای منطق شما هیچ وابستگی مستقیمی به پکیج `fl_chart` ندارد. شما می‌توانید فردا کتابخانه نمودار خود را عوض کنید و فقط نیاز به بازنویسی `ChartBuilder` خواهید داشت، بدون اینکه هیچ تغییری در سیستم‌ها یا کامپوننت‌های منطقی لازم باشد.

Nexus به عنوان یک پایه

Nexus را به عنوان یک شاسی قدرتمند در نظر بگیرید. این فریم‌ورک، موتور، چرخ‌ها و سیستم فرمان را در اختیار شما قرار می‌دهد. اما این شما هستید که با ساختن سیستم‌ها، کامپوننت‌ها و بیلدرهای سفارشی، بدنه، کابین و ویژگی‌های منحصر به فرد خودروی خود را طراحی می‌کنید. این قابلیت گسترش، به شما اجازه می‌دهد تا یک اکوسیستم از ابزارهای قابل استفاده مجدد برای تیم و پروژه‌های آینده خود بسازید.
