مستندات پروژه-محور Nexus

بخش ۵: پل میان منطق و رابط کاربری

چگونه تغییرات داده در دنیای منطق به به‌روزرسانی‌های بصری در ویجت‌های فلاتر تبدیل می‌شوند؟

چالش اصلی: جدایی دنیاها

تا اینجا یاد گرفتیم که تمام منطق ما در `NexusWorld` و توسط `System`ها اجرا می‌شود، در حالی که رابط کاربری ما با ویجت‌های فلاتر ساخته می‌شود. در حالت ایده‌آل (و در نسخه production)، `NexusWorld` در یک ایزولیت (Isolate) کاملاً جداگانه اجرا می‌شود تا از هرگونه تأثیر منفی بر روی ترد اصلی UI جلوگیری کند. این جدایی، یک چالش اساسی ایجاد می‌کند: چگونه این دو دنیا را به هم متصل کنیم؟

پروتکل ارتباطی Nexus

فریم‌ورک Nexus یک جریان داده یک‌طرفه و کارآمد برای حل این مشکل طراحی کرده است:

جریان داده از منطق به UI

System → Component → RenderPacket → FlutterRenderingSystem → Widget

بیایید این مراحل را یک به یک بررسی کنیم:

  1. سیستم، کامپوننت را تغییر می‌دهد: یک `System` منطق خود را اجرا کرده و یک `Component` را به‌روزرسانی می‌کند.
  2. ارسال بسته رندر (`RenderPacket`): فریم‌ورک به طور خودکار تشخیص می‌دهد که کامپوننت تغییر کرده است. سپس آن را به فرمت JSON سریالایز کرده و در یک بسته سبک به نام `RenderPacket` قرار می‌دهد.
  3. عبور از مرز ایزولیت: این `RenderPacket` از طریق `NexusManager` (که ارتباط بین ایزولیت‌ها را مدیریت می‌کند) به ترد UI ارسال می‌شود.
  4. دریافت در `FlutterRenderingSystem`: این کلاس که در سمت UI قرار دارد، بسته‌ها را دریافت کرده و یک "کَش" یا "آینه" از وضعیت کامپوننت‌ها را در خود به‌روز می‌کند.
  5. بازسازی ویجت: ویجت‌هایی که به داده‌های تغییر یافته گوش می‌دهند، از این تغییر مطلع شده و خود را بازسازی (rebuild) می‌کنند.

`FlutterRenderingSystem`: آینه دنیای منطق در UI

کلاس `FlutterRenderingSystem` قلب تپنده لایه UI است. این یک `ChangeNotifier` است که وظایف زیر را بر عهده دارد:

  • مدیریت کش کامپوننت‌ها: آخرین نسخه از تمام کامپوننت‌های سریالایز شده را در یک `Map` نگهداری می‌کند.
  • ارائه داده به ویجت‌ها: ویجت‌ها از طریق متد `get(entityId)` به داده‌های موجود در این کش دسترسی پیدا می‌کنند.
  • اطلاع‌رسانی تغییرات: هنگامی که داده‌ها از طریق `RenderPacket` به‌روز می‌شوند، به ویجت‌های شنونده اطلاع می‌دهد که زمان بازسازی فرا رسیده است.

`IWidgetBuilder`: پلاگین‌های ساخت ویجت

برای جلوگیری از ایجاد یک کلاس `FlutterRenderingSystem` غول‌پیکر و پیچیده، ما منطق ساخت هر بخش از UI را به کلاس‌های کوچکتر و تخصصی به نام `Builder` منتقل می‌کنیم. هر `Builder` اینترفیس `IWidgetBuilder` را پیاده‌سازی می‌کند. 


// File: lib/src/flutter/widget_builder.dart (در پکیج nexus)

abstract class IWidgetBuilder {
  Widget build(
    BuildContext context,
    FlutterRenderingSystem renderingSystem,
    EntityId entityId,
  );
}

در پروژه ما، `AppBarBuilder`، `BodyBuilder` و `NavigationPanelBuilder` نمونه‌هایی از این پلاگین‌ها هستند. بیایید به `AppBarBuilder` نگاه کنیم: 


// File: lib/src/app_bar/app_bar_builder.dart

class AppBarBuilder implements IWidgetBuilder {
  @override
  Widget build(BuildContext context, FlutterRenderingSystem rs, EntityId entityId) {
    // ... بخش‌هایی از کد ...
    return EntityWidgetBuilder( // نکته مهم!
      renderingSystem: rs,
      entityId: entityId,
      builder: (context) {
        // 1. داده مورد نیاز را از کش می‌خواند
        final data = rs.get(entityId);
        // 2. ویجت را با داده‌های خوانده شده می‌سازد
        return Text(data?.title ?? '...');
      },
    );
  }
}

`EntityWidgetBuilder`: جادوی بازسازی بهینه

شاید متوجه `EntityWidgetBuilder` در کد بالا شده باشید. این ویجت کوچک اما قدرتمند، کلید عملکرد بالای UI در Nexus است. به جای اینکه با هر تغییر، کل صفحه بازسازی شود، `EntityWidgetBuilder` فقط و فقط به تغییرات یک موجودیت خاص گوش می‌دهد.

وقتی `FlutterRenderingSystem` یک `RenderPacket` برای موجودیت AppBar دریافت می‌کند، فقط `EntityWidgetBuilder` مربوط به آن موجودیت `setState` را فراخوانی کرده و بازسازی می‌شود. این یعنی فقط ویجت `Text` که عنوان را نمایش می‌دهد آپدیت می‌شود، نه کل `Scaffold` یا صفحه! این همان چیزی است که به آن بازسازی دانه‌ریز (fine-grained rebuilding) می‌گویند.
