مستندات پروژه-محور Nexus

بخش ۳۷: مدیریت پیشرفته لیست‌ها

کالبدشکافی `ListStateSystem` و نحوه پیاده‌سازی فیلتر، مرتب‌سازی و جستجوی کارآمد.

چالش مدیریت مجموعه‌ها

نمایش لیستی از داده‌ها یکی از رایج‌ترین کارها در هر اپلیکیشنی است. اما مدیریت وضعیت‌های این لیست‌ها (مانند فیلتر، مرتب‌سازی، جستجو و صفحه‌بندی) می‌تواند به سرعت کد شما را پیچیده کند. پکیج `nexus` یک راه‌حل عمومی و قدرتمند برای این مشکل ارائه می‌دهد: `ListStateSystem`.

الگوی "موجودیت مدیر لیست" (List Manager Entity)

همانطور که در مثال `CategoryModule` دیدیم، به جای پخش کردن وضعیت لیست در ویجت‌ها یا کنترلرها، ما یک موجودیت مرکزی برای هر لیست می‌سازیم. این موجودیت دو کامپوننت کلیدی دارد:

  • `ListComponent`: این کامپوننت "منبع حقیقت" (Source of Truth) است. این کامپوننت دو لیست از شناسه‌ها را نگه می‌دارد: `allItems` (لیست کامل و فیلتر نشده) و `visibleItems` (لیستی که باید در UI نمایش داده شود).
  • `ListStateComponent`: این کامپوننت، وضعیت فعلی "نمایش" (view) را نگه می‌دارد. شامل معیارهای فیلتر (`filterCriteria`), فیلد مرتب‌سازی (`sortByField`) و عبارت جستجو (`searchQuery`) است.

`ListStateSystem`: پردازشگر مرکزی لیست

`ListStateSystem` یک سیستم عمومی و رویداد-محور است که به عنوان پردازشگر مرکزی برای تمام لیست‌های اپلیکیشن عمل می‌کند. این سیستم به رویدادهای زیر گوش می‌دهد:

  • `UpdateListFilterEvent`
  • `UpdateListSortEvent`
  • `UpdateListSearchEvent`

وقتی یکی از این رویدادها رخ می‌دهد، `ListStateSystem` کارهای زیر را انجام می‌دهد:

  1. موجودیت مدیر لیست مربوطه را با استفاده از `listId` پیدا می‌کند.
  2. `ListStateComponent` آن موجودیت را با داده‌های جدید از رویداد، به‌روز می‌کند.
  3. متد اصلی خود، `_recalculateVisibleItems`، را فراخوانی می‌کند.

کالبدشکافی `_recalculateVisibleItems`

این متد، خط لوله پردازش لیست است: 


void _recalculateVisibleItems(Entity manager) {
  final listComp = manager.get()!;
  final state = manager.get()!;
  
  // ۱. با لیست کامل شروع می‌کند
  var items = List.from(listComp.allItems);

  // ۲. فیلتر را اعمال می‌کند
  if (state.filterCriteria.isNotEmpty) {
    items = items.where((itemId) => /* منطق فیلتر بر اساس BlackboardComponent */).toList();
  }

  // ۳. جستجو را اعمال می‌کند
  if (state.searchQuery.isNotEmpty) {
    items = items.where((itemId) => /* منطق جستجو در تمام فیلدهای متنی */).toList();
  }

  // ۴. مرتب‌سازی را اعمال می‌کند
  if (state.sortByField != null) {
    items.sort((aId, bId) => /* منطق مقایسه بر اساس sortByField */);
  }

  // ۵. کامپوننت لیست را با visibleItems جدید به‌روز می‌کند
  manager.add(ListComponent(
    listId: listComp.listId,
    allItems: listComp.allItems,
    visibleItems: items, // نتیجه نهایی
  ));
}

مقایسه با Redux/BLoC

این الگو شباهت زیادی به داشتن یک `reducer` یا `BLoC` برای مدیریت وضعیت لیست دارد. اما چند مزیت کلیدی دارد:

  • عمومی و قابل استفاده مجدد: شما یک `ListStateSystem` برای کل اپلیکیشن دارید، نه یک BLoC جداگانه برای هر لیست.
  • داده-محور: تمام وضعیت در کامپوننت‌ها ذخیره می‌شود که به راحتی قابل مشاهده، دیباگ و ذخیره‌سازی هستند.
  • یکپارچگی با ECS: این الگو به طور کامل با سایر بخش‌های معماری ECS یکپارچه است. شما می‌توانید به راحتی سیستم‌های دیگری بنویسید که به تغییرات `ListComponent` واکنش نشان دهند.
