بخش ۳۴: جداسازی عمیق UI از منطق

الگوی "کامپوننت ViewModel" برای ایجاد یک لایه ضدفساد بین دنیای منطق و ویجت‌ها.

مشکل: وابستگی پنهان UI به منطق

ما تاکنون دیده‌ایم که چگونه `IWidgetBuilder`ها داده‌ها را مستقیماً از کامپوننت‌های منطقی (مانند `ProfileDataComponent`) می‌خوانند. این روش کار می‌کند، اما یک وابستگی پنهان ایجاد می‌کند: ویجت‌های شما از ساختار داخلی داده‌های منطقی شما آگاه می‌شوند.

اگر فردا تصمیم بگیرید که `ProfileDataComponent` را به دو کامپوننت `UserIdentityComponent` و `UserContactComponent` بشکنید، باید تمام بیلدرهایی را که از آن استفاده می‌کردند، پیدا کرده و اصلاح کنید. این کار شکننده و مستعد خطا است.

راه حل: الگوی کامپوننت ViewModel

برای حل این مشکل، می‌توانیم یک لایه واسطه بین منطق و UI ایجاد کنیم. این لایه، یک کامپوننت خاص است که ما آن را "کامپوننت ViewModel" می‌نامیم.

یک کامپوننت ViewModel، یک کامپوننت `Serializable` است که داده‌ها را دقیقاً به همان شکلی که UI به آن‌ها نیاز دارد، نگهداری می‌کند. این کامپوننت هیچ منطقی ندارد و فقط یک ساختار داده‌ای است که برای نمایش بهینه شده است.

جریان کار جدید:

  1. کامپوننت‌های منطقی: مانند قبل، داده‌های خام را نگهداری می‌کنند (مثلاً `ProfileDataComponent`).
  2. یک سیستم Presenter: یک سیستم جدید (مثلاً `ProfilePresenterSystem`) به تغییرات کامپوننت‌های منطقی گوش می‌دهد.
  3. ساخت کامپوننت ViewModel: این سیستم داده‌های خام را از چندین کامپوننت منطقی جمع‌آوری کرده، آن‌ها را فرمت می‌کند (مثلاً تبدیل تاریخ به رشته) و یک کامپوننت ViewModel (مثلاً `ProfileViewComponent`) را می‌سازد یا به‌روز می‌کند.
  4. بیلدر UI: بیلدر (`ProfilePanelBuilder`) دیگر مستقیماً به کامپوننت‌های منطقی دسترسی ندارد. در عوض، فقط و فقط کامپوننت `ProfileViewComponent` را می‌خواند و داده‌های آماده آن را نمایش می‌دهد.

// ۱. کامپوننت ViewModel
class ProfileViewComponent extends Component with SerializableComponent {
  final String fullName;
  final String displayAge; // داده فرمت شده برای نمایش
  final String contactInfo;
  // ...
}

// ۲. سیستم Presenter
class ProfilePresenterSystem extends System {
  @override
  bool matches(Entity entity) {
    // به موجودیت‌هایی که داده منطقی دارند اما ViewModel ندارند (یا نیاز به آپدیت دارند) گوش می‌دهد
    return entity.has() && entity.isDirty();
  }

  @override
  void update(Entity entity, double dt) {
    final data = entity.get()!;
    
    // منطق تبدیل و فرمت کردن داده‌ها
    final viewModel = ProfileViewComponent(
      fullName: data.name,
      displayAge: "سن: ${data.age} سال",
      contactInfo: "ایمیل: ${data.email}",
    );
    
    entity.add(viewModel);
  }
}

// ۳. بیلدر UI
class ProfilePanelBuilder implements IWidgetBuilder {
  @override
  Widget build(BuildContext context, FlutterRenderingSystem rs, EntityId entityId) {
    return EntityWidgetBuilder(
      // ...
      builder: (context) {
        // بیلدر فقط ViewModel را می‌شناسد و به جزئیات منطق کاری ندارد
        final view = rs.get(entityId);
        return Column(children: [
          Text(view?.fullName ?? ""),
          Text(view?.displayAge ?? ""),
        ]);
      },
    );
  }
}

مزایای لایه ViewModel

  • جداسازی کامل (Decoupling): لایه UI کاملاً از ساختار داده‌های منطقی جدا می‌شود. شما می‌توانید منطق را بدون شکستن UI تغییر دهید.
  • سادگی در UI: بیلدرها بسیار ساده و "احمق" می‌شوند. آن‌ها فقط داده‌های آماده را نمایش می‌دهند و هیچ منطق فرمت‌بندی یا ترکیبی در آن‌ها وجود ندارد.
  • قابلیت تست: `ProfilePresenterSystem` را می‌توان به راحتی تست کرد. شما کامپوننت‌های منطقی را به عنوان ورودی به آن می‌دهید و بررسی می‌کنید که آیا کامپوننت ViewModel صحیح را به عنوان خروجی تولید می‌کند یا خیر.

اگرچه این الگو کمی کدنویسی اولیه را افزایش می‌دهد، اما برای پروژه‌های بزرگ و پیچیده، یک سرمایه‌گذاری ارزشمند است که به شدت به نگهداری و توسعه‌پذیری کد در دراز مدت کمک می‌کند.
