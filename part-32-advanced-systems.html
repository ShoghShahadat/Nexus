مستندات پروژه-محور Nexus

بخش ۳۲: الگوهای پیشرفته طراحی سیستم

چگونه سیستم‌هایی بنویسیم که نه تنها کار کنند، بلکه تمیز، کارآمد و قابل ترکیب باشند.

سیستم به عنوان یک تابع خالص

در بخش ۲۵، بهترین شیوه‌های اولیه برای نوشتن سیستم‌ها را بررسی کردیم. در این بخش، یک قدم فراتر رفته و به الگوهای پیشرفته‌تری می‌پردازیم که به شما کمک می‌کنند تا منطق خود را به صورت یک خط لوله پردازش داده (Data Processing Pipeline) طراحی کنید.

ایده اصلی این است که به یک سیستم به عنوان یک تابع خالص نگاه کنیم: مجموعه‌ای از کامپوننت‌ها را به عنوان ورودی می‌گیرد و مجموعه‌ای از کامپوننت‌های جدید یا به‌روز شده را به عنوان خروجی تولید می‌کند، بدون اینکه وضعیت داخلی داشته باشد.

الگوی سیستم‌های زنجیره‌ای (Chained Systems)

گاهی اوقات یک منطق پیچیده را می‌توان به چند مرحله پردازشی کوچکتر شکست. به جای اینکه تمام این مراحل را در یک سیستم بزرگ پیاده‌سازی کنیم، می‌توانیم چندین سیستم کوچک بسازیم که خروجی یکی، ورودی دیگری باشد. این ارتباط از طریق رویدادها یا کامپوننت‌های نشانگر برقرار می‌شود.

مثال: پردازش آسیب در یک بازی

وقتی یک بازیکن آسیب می‌بیند، چندین اتفاق باید رخ دهد: کاهش سلامتی، بررسی مرگ، اعمال افکت‌های بصری، و به‌روزرسانی UI.

رویکرد بد (یک سیستم بزرگ):


class DamageSystem extends System {
  void _onCollision(CollisionEvent event) {
    // 1. کاهش سلامتی
    // 2. اگر سلامتی صفر شد، کامپوننت IsDead را اضافه کن
    // 3. کامپوننت DamageEffect را برای نمایش انیمیشن اضافه کن
    // 4. کامپوننت HealthBarUIChanged را برای آپدیت UI اضافه کن
    // ... این سیستم بیش از حد مسئولیت دارد
  }
}

رویکرد خوب (سیستم‌های زنجیره‌ای):

  1. DamageSystem: فقط به `CollisionEvent` گوش می‌دهد و `HealthComponent` را به‌روز می‌کند. اگر سلامتی تغییر کرد، رویداد `HealthChangedEvent` را منتشر می‌کند.
  2. DeathSystem: به `HealthChangedEvent` گوش می‌دهد. اگر سلامتی صفر یا کمتر باشد، کامپوننت `IsDeadComponent` را اضافه می‌کند.
  3. DamageEffectSystem: به `HealthChangedEvent` گوش می‌دهد و یک `AnimationComponent` برای نمایش افکت آسیب به موجودیت اضافه می‌کند.
  4. HealthBarUISystem: به `HealthChangedEvent` گوش می‌دهد و کامپوننت مربوط به UI نوار سلامتی را به‌روز می‌کند.

در این رویکرد، هر سیستم یک کار کوچک و مشخص را انجام می‌دهد. این سیستم‌ها کاملاً از هم جدا هستند و می‌توان آن‌ها را به راحتی تست، تغییر یا حذف کرد.

ترتیب اجرای سیستم‌ها (System Execution Order)

در Nexus، سیستم‌ها به همان ترتیبی که به `NexusWorld` اضافه می‌شوند، در هر فریم اجرا می‌گردند. این ترتیب در اکثر موارد اهمیتی ندارد، زیرا سیستم‌ها باید مستقل از هم طراحی شوند. اما در موارد نادری (مخصوصاً در فیزیک بازی)، ترتیب اجرا می‌تواند مهم باشد. 


// در worldProvider

// ابتدا ورودی پردازش می‌شود
world.loadModule(InputModule()); 
// سپس فیزیک و حرکت بر اساس ورودی محاسبه می‌شود
world.loadModule(PhysicsModule()); 
// در نهایت، دوربین بر اساس موقعیت جدید، آپدیت می‌شود
world.loadModule(CameraModule());

با کنترل ترتیب بارگذاری ماژول‌ها، شما می‌توانید یک خط لوله پردازشی قابل پیش‌بینی برای هر فریم ایجاد کنید.

مقایسه با متدهای بزرگ در MVVM/BLoC

در معماری‌های دیگر، معمولاً با متدهایی مواجه می‌شویم که چندین کار را پشت سر هم انجام می‌دهند. این متدها به سرعت طولانی و پیچیده می‌شوند. الگوی سیستم‌های زنجیره‌ای در Nexus، شما را تشویق می‌کند تا این منطق‌های طولانی را به واحدهای کوچک، مستقل و قابل ترکیب بشکنید. این مانند ساختن یک خط لوله با لوله‌های کوچک و استاندارد است، به جای ساختن یک لوله غول‌پیکر و یکپارچه.
