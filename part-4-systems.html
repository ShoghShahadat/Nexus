مستندات پروژه-محور Nexus

بخش ۴: سیستم‌ها، مغز متفکر معماری

آشنایی با `System`، جایی که تمام منطق برنامه شما در آن زنده می‌شود.

System: جایی که منطق اتفاق می‌افتد

تا به اینجا، ما "چیزها" (Entities) و "داده‌هایشان" (Components) را تعریف کرده‌ایم. اما این دو به تنهایی بی‌جان هستند. قطعه سوم و نهایی پازل ECS، System (سیستم) است. سیستم‌ها، کارگران خط تولید ما هستند؛ آن‌ها منطق برنامه را اجرا می‌کنند. هر سیستم یک وظیفه کاملاً مشخص دارد و فقط روی موجودیت‌هایی کار می‌کند که داده‌های مورد نیازش را داشته باشند.

دو نوع اصلی منطق در سیستم‌ها

در فریم‌ورک Nexus، سیستم‌ها می‌توانند منطق خود را به دو روش اصلی اجرا کنند:

  1. منطق مبتنی بر کوئری (Query-Based): سیستم در هر فریم (یا تیک منطقی)، تمام موجودیت‌هایی را که با یک الگوی خاص از کامپوننت‌ها مطابقت دارند، پیدا کرده و روی آن‌ها یک عملیات را اجرا می‌کند. این روش برای کارهای مداوم مانند حرکت فیزیکی یا انیمیشن ایده‌آل است.
  2. منطق رویداد-محور (Event-Driven): سیستم به رویدادهای خاصی که در اپلیکیشن رخ می‌دهند (مانند کلیک کاربر) گوش می‌دهد و فقط در پاسخ به آن رویدادها فعال می‌شود. این روش برای واکنش به تعاملات کاربر بسیار کارآمد است.

غواصی عمیق: `AppBarSystem` (منطق رویداد-محور)

بیایید به `lib/src/app_bar/app_bar_module.dart` نگاهی بیندازیم. این سیستم مسئول به‌روزرسانی عنوان AppBar هنگام تغییر صفحه است. 


// File: lib/src/app_bar/app_bar_module.dart

class AppBarSystem extends System {
  @override
  void onAddedToWorld(NexusWorld world) {
    super.onAddedToWorld(world);
    // 1. به محض اضافه شدن به دنیا، شروع به گوش دادن به رویداد می‌کند
    listen((event) {
      // 2. موجودیت AppBar را پیدا می‌کند
      final appBarEntity =
          world.entities.values.firstWhere((e) => e.has());
      
      // 3. کامپوننت داده آن را با عنوان جدید به‌روزرسانی می‌کند
      appBarEntity.add(AppBarComponent(title: event.title));
    });
  }

  // این سیستم نیازی به حلقه update ندارد، پس این متدها خالی می‌مانند
  @override
  bool matches(Entity entity) => false;

  @override
  void update(Entity entity, double dt) {}
}

این یک مثال بی‌نقص از یک سیستم رویداد-محور است. `AppBarSystem` هیچ کاری انجام نمی‌دهد تا زمانی که رویداد `NavigationItemTappedEvent` رخ دهد. این رویکرد بسیار بهینه است زیرا از اجرای کدهای غیرضروری جلوگیری می‌کند.

متد `matches` و حلقه `update`

حالا بیایید به نوع دیگر سیستم‌ها بپردازیم. سیستم‌های مبتنی بر کوئری از دو متد کلیدی استفاده می‌کنند:

  • `bool matches(Entity entity)`: این متد برای هر موجودیت در دنیا فراخوانی می‌شود. اگر `true` برگرداند، یعنی این سیستم به این موجودیت "علاقه‌مند" است.
  • `void update(Entity entity, double dt)`: این متد در هر فریم، فقط برای موجودیت‌هایی که `matches` برای آن‌ها `true` بوده است، اجرا می‌شود. `dt` یا دلتا تایم، زمان سپری شده از فریم قبلی است.

مثال: `PhysicsSystem`

یک سیستم فیزیک کلاسیک در ECS به این شکل خواهد بود: 


class PhysicsSystem extends System {
  // 1. به موجودیت‌هایی علاقه‌مند است که هم موقعیت و هم سرعت دارند
  @override
  bool matches(Entity entity) {
    return entity.has() && entity.has();
  }

  // 2. در هر فریم، موقعیت را بر اساس سرعت به‌روز می‌کند
  @override
  void update(Entity entity, double dt) {
    final pos = entity.get()!;
    final vel = entity.get()!;

    pos.x += vel.x * dt;
    pos.y += vel.y * dt;

    // کامپوننت را دوباره اضافه می‌کنیم تا فریم‌ورک متوجه تغییر شود
    entity.add(pos);
  }
}

جمع‌بندی و نگاه به آینده

ما سه قطعه اصلی پازل را تکمیل کردیم:

  • Entity: شناسه
  • Component: داده
  • System: منطق

سیستم‌ها با خواندن داده‌ها از کامپوننت‌ها، اجرای منطق و سپس نوشتن نتایج در کامپوننت‌های دیگر، وضعیت اپلیکیشن را به پیش می‌برند. اما چگونه این تغییرات داده در دنیای منطق، به تغییرات بصری در UI فلاتر تبدیل می‌شود؟ این سوال هیجان‌انگیز، موضوع بخش بعدی ما خواهد بود.
